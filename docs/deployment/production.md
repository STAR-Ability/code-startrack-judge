# Production deployment

There is no production release, service image, or qualified sandbox profile yet. Phase 0 prepares engineering rules and portable infrastructure; it is not deployable judge functionality. The current target is V0.2; use the [active contract pointer](../contracts/README.md) and [release process](../releases/process.md), rather than interpreting this document as a release announcement.

## Deployment boundary

The current contract calls for four business containers in the whole platform, with this repository delivering one judge container. Its supervised processes are non-root API/persistent worker, demo judger adapter, and go-judge. API binds `0.0.0.0:8082` on the private service network. go-judge binds `127.0.0.1:5050`, is not published on the host, and receives a separate low-level token. Do not introduce a fifth business container or expose upstream bare submit/shell endpoints as a shortcut.

Provide modern Linux/cgroup v2, tested namespace/seccomp support, reviewed cgroup delegation and a tested restricted capability/mount profile. `--no-fallback` is mandatory; `--no-seccomp` is forbidden. Ordinary Docker and Docker Desktop do not establish this profile. `privileged: true` is not the production default. Required privileges for the sandbox manager must be justified by pinned upstream behavior, narrowly scoped, and independently reviewed. API/worker remain non-root; executable children receive neither service credentials nor host access.

Private storage contains immutable originals/normalized packages, hidden tests, reference code, validation evidence, and restricted logs. Mount only each execution's files and controlled toolchains into its sandbox; no host-root, backend-source storage, or Docker socket. Judge credentials can access only judge schema/private storage. Use a separate narrowly scoped migration identity; never deploy development bootstrap/admin DB credentials. Deny executable network traffic and isolate service network exposure. Scope S2S and storage secrets per process and rotate them independently.

## Upgrade runbook

1. Select a release whose record contains tested backend/contract compatibility, current/target migration levels, immutable image digest, upstream/toolchain pins, sanitized CI and real Linux qualification reports, license/NOTICE/SBOM inventory, and rollback limits. Resolve release-blocking contract questions and the project-license decision before publishing.
2. Capture the existing release commit/image/digests, migration checksum inventory, relevant configuration hashes, queue/outbox counts, and storage manifest. Make a consistent protected DB backup and verify restore on a separate environment; include immutable private objects and license/validation evidence. Set recovery-point/time expectations suitable for the deployment; do not claim backup safety from backup creation alone.
3. Validate the proposed migration on a restored dataset with realistic history. Review lock duration, disk growth, concurrent writes, and application compatibility. Use the [migration policy](../../migrations/README.md); do not rewrite shipped files or perform undocumented manual SQL.
4. Enter the documented maintenance/admission-drain mode. Stop accepting new execution while allowing authorized history queries where dependencies permit. Drain or fence ongoing work according to the active contract, preserving durable task/outbox state; never discard acknowledged jobs. Avoid concurrent old/new workers changing final facts. Scope maintenance to judge, preserving unrelated backend business.
5. Apply forward migrations using the controlled migration command and migration identity. Record the resulting schema level/checksums. If a migration fails, keep readiness unavailable, preserve error evidence privately, inspect transaction/schema state, and repair using a reviewed forward change; do not mark a dirty/partial state clean without evidence.
6. Deploy the recorded immutable digest with the qualified Linux profile and operator-owned secrets. Recheck actual cgroup/namespace/seccomp/filesystem/network/limits behavior on that profile. Verify `/health` behavior against the contract: dependencies/self-checks pass for 200; otherwise 503 and `judge=false` disables new execution while available history reads may continue.
7. Run synthetic catalog/judge/import smoke tests, backend callback and polling/reconciliation checks, queue/lease recovery, private-data-leak checks, and old problem-version/task reads. Verify old tasks retain their frozen package, limits, toolchain/template and sandbox context. Enable admission only after evidence passes.
8. Observe queue age, expired leases, execution failures, storage failures, callback retries/dead letters, authentication failures, resource pressure, and isolation readiness. Record deployment time/operator/environment, actual digest, migration level and evidence in the release record. Alerts use identifiers and structured codes, not source/tests/secrets.

Application rollback is possible only if the previous binary supports the migrated schema and frozen task/runtime context. Retain supported historical toolchain images/artifacts needed by accepted work. Otherwise stay in maintenance and use a reviewed forward fix; database restore is a separate disaster-recovery action that can lose later acknowledged facts and requires explicit incident ownership, a coordinated DB/object point, and backend reconciliation. Never delete history or rewind migrations to make an old image start.

## Incidents and recovery

On isolation failure stop new execution immediately and isolate the host; do not fall back to ordinary execution. Inspect in-flight tasks/leases, retain evidence, and use fenced recovery on a qualified clean host. Callback auth/conflict/unknown-task failures remain durable for investigation; do not fake delivery. A dead-letter replay needs the unchanged event identity/payload and backend reconciliation, not a new task or mutated historical result.

Restore drills must prove task/result/outbox consistency, package checksum and license-evidence access, migration visibility, backend request/task mapping, and historical version reads. Privacy and archival retention policies, operator reporting contacts, host provider/profile, and final secret facility are owner/operator decisions to record before production. They are not implied by the portable Compose environment.
