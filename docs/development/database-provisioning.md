# Database role provisioning

Use PostgreSQL 17 and separately scoped operator, migration and runtime credentials. [provision-db.sql](../../scripts/provision-db.sql) creates the fixed `judge_migration` and `judge_runtime` roles and the migration-owned `judge` schema before the forward runner starts. Both service roles have no superuser, role/database creation, replication, bypass-RLS, inheritance or role memberships. The runtime receives schema USAGE and business DML only after migration. Search paths are a convenience; actual grants enforce ownership.

The operator connects using normal libpq secret facilities such as a protected service/password file, with verified TLS for network connections. Supply `JUDGE_MIGRATION_PASSWORD` and `JUDGE_RUNTIME_PASSWORD` through the operator's environment; each is independent and at least 32 characters. Do not put passwords in shell history, command arguments, SQL files or logs. Use `psql --no-psqlrc --file scripts/provision-db.sql`, run the native migration with `JUDGE_MIGRATION_DATABASE_URL`, then `psql --no-psqlrc --file scripts/grant-runtime.sql`. The provisioning script disables session SQL/parameter/error-statement logging before it interpolates passwords, and fails before using them when the operator lacks permission to do so. Verify any external SQL proxy/auditor's secret policy separately; do not run password provisioning through a layer that records raw statements. These operator-only settings never enter the application or sandbox environment.

The database must already deny runtime permanent and temporary object creation and deny both service roles access to other services' relations. PostgreSQL normally grants PUBLIC temporary-table creation, so a dedicated Judge database needs an explicit operator-reviewed database ACL baseline that revokes PUBLIC TEMPORARY before provisioning. On a shared database, arrange explicit grants for the other owners first; this repository's provisioning command refuses unsafe defaults instead of changing their privileges. It also refuses another schema owner or unsafe existing role attributes/memberships. A failed invocation rolls back its whole transaction. Record the reviewed infrastructure ACL baseline and verify denials with the actual roles.

Repeated provisioning validates and retains existing roles/passwords. Password rotation is a separate operator action; supplying new values does not silently overwrite credentials. Reapply the explicit runtime grants after a forward migration adds owned tables. Never grant runtime write access to `judge.schema_migrations` or `judge.migration_checksums`, DDL privileges, arbitrary new schemas or Backend/Algorithm relations. Verify these boundaries before release; having the SQL files alone is not acceptance evidence.
