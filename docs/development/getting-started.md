# Portable development

Phase 0 supplies a reproducible PostgreSQL environment and exact upstream source
verification. The service, judge schema, migration runner, API and workers have
not been implemented. There is no `make run` command or working judge endpoint
yet. Follow the [implementation plan](../architecture/implementation-plan.md)
for the next milestones.

## Requirements and first use

Use macOS or Linux with Python **3.11 or later**, Git, Make, Docker Engine or a
local Docker VM, and Docker Compose **2.20 or later**. Foundation scripts use
only the Python standard library; no `pip install` is needed. Start Docker
Desktop, Colima (`colima start`), or your Linux Docker engine before `infra-up`.
These scripts check dependencies but do not install software or start your host
Docker VM. Docker access is trusted local administration, never a sandbox grant.

```sh
git clone https://github.com/STAR-Ability/code-startrack-judge.git
cd code-startrack-judge
git switch dev
make bootstrap
make check
make infra-up
make db-version
make migration-status
make upstream-fetch
make upstream-verify
make infra-down
```

`bootstrap` validates the tools and Compose configuration, and creates a random
local password in ignored `.env` with mode `0600`. It retains an existing file
without replacing your settings or printing secrets. A malformed/insecure file
fails with instructions. `.env.example` documents settings; its password is a
placeholder, and copying it directly will not start infrastructure through the
scripts. `make check` and upstream source verification do not require Docker to
be running. The default host port is `127.0.0.1:15432`.

`infra-up` waits for PostgreSQL's health check and fails on errors/timeouts.
`infra-down` stops containers and retains the named database volume. `db-version`
queries the actual running PostgreSQL server; it is **not** a schema version.
`migration-status` currently reports repository level **0**, no SQL and no
installed migration tracking. It does not certify the contents of a connected
database. [Migration policy](../../migrations/README.md) owns the later workflow.

## Environment reference

Only the following settings are consumed in Phase 0. Values in `.env` explicitly
win over a same-named variable in the invoking shell. Use simple unquoted values
without interpolation; tokens generated by bootstrap meet this format.

| Variable | Local default / purpose |
| --- | --- |
| `COMPOSE_PROJECT_NAME` | `startrack-judge-dev`; lowercase project/volume namespace. Use a distinct name for a parallel isolated environment. |
| `POSTGRES_USER` | `judge_dev`; development database administrator initialized by the official PostgreSQL image. Letter followed by letters/digits/underscores, at most 63 characters. |
| `POSTGRES_DB` | `judge_dev`; initial local database, same identifier rules. |
| `POSTGRES_PASSWORD` | Generated random local secret (at least 32 characters). Kept only in ignored `.env`; the example placeholder is rejected. |
| `POSTGRES_PORT` | `15432`; host TCP port, restricted to `127.0.0.1`, valid range 1024–65535. |
| `INFRA_WAIT_SECONDS` | `90`; maximum Compose health wait, range 1–600 seconds. Image downloads may take additional time. |

`PYTHON` is an optional Make override selecting a Python >=3.11 executable,
for example `make PYTHON=python3.12 check`. It is not a service setting.

The development `POSTGRES_USER` is an image initialization administrator,
**not** the future application account. The first schema Issue must introduce
reviewed migration and application roles scoped to the `judge` schema, without
backend or algorithm credentials. This Compose stack is not a production
database configuration. Local container inspection can reveal its environment;
protect your host account and never reuse local passwords in shared environments.

PostgreSQL image initialization variables apply only to an empty volume.
Changing a password, database name or user in `.env` does not change an existing
database. Retain the volume and use deliberate SQL administration if needed;
for a fresh independent experiment, change `COMPOSE_PROJECT_NAME`. A port clash
can be resolved by changing `POSTGRES_PORT` while the stack is stopped. Never
remove an unknown user's volume or use destructive reset commands as a fix.

The image is pinned to `postgres:17.10-bookworm` and an exact multi-platform
registry index digest in [compose.yaml](../../compose.yaml). A future update
must review PostgreSQL release notes, compatibility/security, and the new
digest through an Issue. Support for Linux amd64/arm64 comes from that manifest;
a macOS Docker VM supports portable infrastructure, not production isolation.

## Upstream source cache

`upstream-fetch` reads [upstream.lock.json](../../upstream.lock.json) and fetches
only full immutable commits into ignored **bare** repositories at
`.cache/upstream/<component>.git`. It does not check out files, initialize
submodules, execute upstream code/hooks, install Python packages, or compile
programs. It verifies the commit objects, Git integrity, and retained license
bytes. `upstream-verify` performs those checks offline; a missing cache is an
error directing you to fetch. Existing caches with an unexpected origin are
preserved and rejected. Public HTTPS Git access is required only for fetch;
normal `HTTPS_PROXY`/`HTTP_PROXY` settings may be used by Git, and global Git
configuration is disabled for this retrieval command.

Fetch one source when useful:

```sh
python3 scripts/upstream.py fetch --component go-judge
python3 scripts/upstream.py verify --component go-judge
git --git-dir .cache/upstream/go-judge.git show e9d70a0d9a3df0c62182a6e7090d7af650a1d5f8:go.mod
```

The pinned Go components require Go **1.26.0** and problemtools requires Python
>=3.11, but upstream **build/install tooling is deferred** until its implementing
Issue establishes locked transitive dependencies and a reproducible toolchain.
Source retrieval is not runtime compatibility or package-license approval.
See the [upstream inventory](../upstream/dependencies.md) and
[compatibility matrix](../upstream/compatibility-matrix.md).

## Service development and sandbox validation

The next implementation step will add service configuration and native
language tooling; database migration and service start commands must be added
and verified in their Issues. Portable tests may exercise DTOs, repositories,
parsers and mocks as those exist. They must not execute untrusted submissions,
validators, checkers or reference programs on the host.

`make sandbox-preflight` only checks Linux prerequisites. It fails on macOS;
success is **not** proof that resource and isolation controls work. Real judge
validation belongs on dedicated Linux infrastructure and follows
[Linux sandbox validation](linux-sandbox.md). Never add an unrestricted execution
fallback to make portable tests pass.
