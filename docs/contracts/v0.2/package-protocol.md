# Immutable problem manifest and checker protocol 0.2.0

Q-007 engineering profile, authorized 2026-10-08 for `ojlab-kattis-v0.2.1` and source `oj-lab-v1`. The exact [manifest schema](manifest-schema.json) and [validation-results schema](validation-results-schema.json) are normative typed inputs. JSON property names, required/null behavior, enum values and limits are exact; there are no accepted synonym fields. Objects reject unknown fields except intentionally retained sourceMetadata and originalValue/normalizedValue in adaptation evidence. Strict UTF-8/duplicate-member validation and [JCS hashing](clarifications.md#q-002-canonical-serialization-and-hash-boundaries) apply before schema validation.

This is a private artifact/runtime protocol. It does not add package/test/path/command fields to submission APIs. Source/normalized archive checksums, evidence bindings, actual validation image/toolchain identity and selected run live in artifact/validation-context records outside the byte-derived manifest. Including an archive's own digest in its bytes would create a circular checksum and is forbidden.

## Supported mode and file identity

The current profile supports `BATCH_PASS_FAIL`, public submission language `cpp17`, and the pinned Kattis default output checker. Interactive, output-only, scoring/group graders, custom output-checker programs, unsupported per-group test semantics, VIVA validators and unknown execution-affecting flags are `PACKAGE_UNSUPPORTED`. Preserve original bytes and unsupported evidence; do not silently downgrade them. The manifest carries languageIds exactly `["cpp17"]`; internal reference/input-validator languages may be `cpp17` or pinned, isolated `python3`, and do not become public submission capabilities.

Every file reference contains canonical normalized relative path, exact byte SHA-256 and exact byte size. The inventory maps each original path to a normalized path with both digests/sizes; generated files use explicit null originalPath/sourceSha256/sourceSizeBytes. Original files are retained even when their validation view is generated. Inventory paths are unique, safe, case-sensitive and agree with stored bytes. No arbitrary OS path, URL, symlink, hardlink, device, FIFO or socket is valid.

Runtime validation additionally enforces contiguous test ordinal `1..testCount`, equality of testCount and tests length, unique case input/answer pairs, references present in the inventory with matching role/digest/size, source/normalized mapping consistency and accepted reference presence. Both SAMPLE and SECRET tests are required for publication. Sample cases precede secret cases; within each visibility group, sort normalized input paths by their raw UTF-8 bytes. An answer matches its input's exact source stem and cannot be borrowed from a different case. An unrecognized source ordering directive is unsupported rather than silently ignored. All case checker configurations are frozen in the manifest.

In this first profile every case checker equals the manifest's global checker exactly. A source case/group flag that changes checker or validation behavior is PACKAGE_UNSUPPORTED unless identical to the already-frozen global configuration; it is never ignored. validationGroup may retain an original grouping label without introducing scoring/order/limit/validator semantics. Future support for differing per-case configuration requires a real adapter-profile upgrade and corresponding legacy verification mapping.

Manifest files sort by raw UTF-8 normalizedPath bytes; referenceSolutions and inputValidators sort by their FileRef path bytes. Each normalized inventory path and each program source path within its category is unique. Adaptations sort by sourceField UTF-8 bytes, then code UTF-8 bytes, then the complete adaptation's JCS bytes; identical adaptation objects are deduplicated. The tests array retains the ordinal order above. SourceMetadata arrays retain source order. No filesystem traversal order or map iteration order enters a hash.

The legacy shortname is `p` followed by the first 32 lowercase hexadecimal digits of SHA-256 over the exact UTF-8 source packagePath. Detect and reject a collision instead of replacing another package. Retain the original shortname and mapping evidence. The full Markdown statement remains the public source; create a separately escaped TeX validation view at exactly `problem_statement/problem.en.tex`, and record its generated bytes/checksum. Its bytes begin `\problemname{<escaped-title>}` followed by one LF, followed by the complete escaped Markdown text and one final LF if absent. In one pass over original characters, the deterministic literal escaping maps backslash→`\textbackslash{}`, braces→`\{`/`\}`, dollar→`\$`, ampersand→`\&`, hash→`\#`, percent→`\%`, underscore→`\_`, caret→`\textasciicircum{}`, tilde→`\textasciitilde{}`; all other Unicode scalar values are retained. The view converts CRLF/lone CR to LF, tab to four spaces, and each LF to `\par{}` followed by LF; record those validation-view adaptations while preserving source bytes verbatim. This is a literal validation view, not a claim to preserve Markdown rendering. Never modify the Markdown source to satisfy legacy tools. TeX tooling, input validators, reference solutions and checker executions are untrusted and require isolated validation profiles.

## Units, bounded profiles and adaptation evidence

The exact pinned package source defines `.timelimit` in seconds. Parse a bounded finite positive decimal lexeme using exact decimal arithmetic, multiply by 1000, and reject a value whose milliseconds are not integral. Missing/invalid time configuration is `PACKAGE_INVALID`; this profile invents no CPU default. Preserve the raw lexeme and conversion evidence. Source `limits.memory` and `limits.output` are MiB, multiplied exactly by 1,048,576; absent values use pinned problemtools defaults only with explicit DEFAULT_APPLIED evidence.

| Limit | Frozen profile |
|---|---|
| Submission CPU | Source seconds ×1000; positive, maximum60,000ms. |
| Submission wall | Exactly2×CPU; maximum120,000ms. This is an owned documented policy, not source metadata or UI inference. |
| Submission memory | Source MiB ×1,048,576; default1,024MiB; maximum2GiB. |
| Submission output | Source MiB ×1,048,576; default8MiB; maximum64MiB. |

Out-of-profile source limits or execution semantics are rejected with retained original evidence, never clamped. Compiler resource/diagnostic-output exhaustion caused by submitted source is a bounded CE diagnostic; missing compiler, broken sandbox or toolchain infrastructure is IE. Compiler output is not allowed to escape the sandbox while reporting CE. Checker failure is always IE, including checker resource exhaustion, rather than blaming contestant output as WA.

The legacy verification view stores `problem.yaml` as JCS JSON (valid YAML) without trailing newline: name is the source title string, type is `pass-fail`, validation is `default`, validator_flags is the deterministic generated default-checker flag string, and limits contains memory/output in exact MiB plus code128,compilation_time60,compilation_memory1024,validation_time60,validation_memory1024,validation_output8,time_multiplier5,time_safety_margin2. Original YAML and extension fields are retained separately in the source archive/manifest evidence. The source title comes from its original scalar name; unsupported structured/multilingual source names are classified explicitly rather than guessed. `validator_flags` contains only the allowlisted output-checker flags, never input-validator arguments.

Pinned legacy metadata does not parse `.timelimit` or accept `limits.time_limit`. The controlled verifyproblem invocation therefore supplies `--fixed_timelim` with the exact frozen CPU milliseconds divided by1000 as a generated decimal seconds argument, one thread, no data/submission filters and all required parts. Caller flags are impossible. Retain all upstream technical errors. Upstream fixed-limit/sample-warning/extra-time allowances are not sufficient publication evidence: independently require every ACCEPTED reference to be AC on every SAMPLE and SECRET case under the exact frozen CPU/wall/memory/output profile and checker, with per-reference/per-case evidence. A sample warning or success only at the upstream relaxed high time limit cannot make referenceSolutions.passed=true.

Every applied conversion, default, Markdown/TeX view, shortname mapping and metadata extension relocation produces typed adaptation evidence with sourceField, originalValue, normalizedValue and reason. SourceMetadata preserves original title/tags/difficulty and unknown extension values; raw metadata files also remain in the original inventory. No upstream difficulty number becomes PLATFORM_RATING/CF_RATING automatically. Effective limits and metadata must agree with immutable problem-version fields and with task admission's frozen execution limits.

At the pinned OJ-Lab revision, all14 packages use CPU1–4 seconds and output8MiB;13 use memory1,024MiB and hello-world2,048MiB. All14 contain an accepted C++ reference; hello-world additionally has Python reference and its only Python input validator. The other13 contain no input format validator; the pinned problemtools reports this as a real technical failure. Do not create invented validators or declare all14 publishable. Python3 is an internal qualified validation capability with actual pinned identity, not a public V0.2 language.

## Canonical archive bytes and safe ingestion

The archive profile is `startrack-ustar-v1`: an uncompressed POSIX ustar TAR of regular files only, sorted by raw UTF-8 relative path bytes. It contains no directory entries, PAX/GNU extensions, sparse entries, links or special files. Headers use owner/group IDs0, empty owner/group names, mtime0, zero device IDs, regular-file type and mode0644 for every member. Source executable mode is retained in provenance rather than trusted. Compiled executable outputs live outside these immutable source/normalized archives and have separate validation/runtime evidence. File names use exact UTF-8 bytes; paths must fit the ustar100-byte name/155-byte prefix representation, with rightmost valid slash split when needed. The magic bytes are `ustar` followed by NUL, version bytes `00`, and unused header bytes are zero. Header numeric values are zero-padded octal, checksum uses the standard six octal digits/NUL/space, file contents are padded with zero bytes to512, and the archive ends with exactly two zero512-byte blocks. There is no extra block padding or appended data. Archive builder golden fixtures must prove cross-implementation byte fidelity before artifact acceptance.

Both original-source archive construction and normalized-view archive construction use this profile; manifest JSON bytes in the normalized archive are JCS without trailing newline. Original archive excludes the derived manifest; normalized archive contains it without embedding either archive digest. Fixed source/adapter identities must produce identical source/normalized bytes and byte-derived manifest. Q-005's separate immutable source/content identities enforce this across evidence changes. Compression is a transport detail only if separately recorded; stored checksum bytes remain the uncompressed defined archive.

The normalized archive's exact reserved manifest path is `startrack-manifest.json`. It is an implicit generated archive member, excluded from the manifest's files inventory and from every FileRef; the manifest therefore never contains its own checksum. A source package containing that reserved root path is `PACKAGE_UNSUPPORTED` with retained originals instead of an overwrite or rename. The reserved member participates in archive sorting and its byte size counts toward archive safety limits. No other member may use the reserved path.

The [archive golden vectors](../../../testdata/archive-golden.json) freeze simple text, arbitrary binary bytes/order and the rightmost-valid prefix split, including complete base64 archive bytes and SHA-256. These are synthetic format vectors, not validated problem packages. The implementation's builder must independently reproduce their exact bytes; the schema test script currently verifies the vector integrity, standard-parser content and profile metadata.

Before object registration, enforce maximum64MiB per file,512MiB total extracted regular-file bytes,65,536 files and4,096 tests. Validate headers, checksums, path representation, duplicate paths and declared sizes without trusting extension records. Reject absolute/traversal/backslash/control/percent-encoded interpretations and noncanonical paths, NUL truncation, escaping links, case-fold ambiguity on portable extraction, oversized/truncated archives and trailing archive entries. Extract only into a newly allocated private directory with no symlink-following or overwrite. Never execute source during extraction. An unsafe original archive may be retained inert as private rejection evidence; it never becomes an accepted execution artifact.

## Default checker invocation and verdicts

Implementation is exact `Kattis/problemtools` commit `6010cbaa37a1612117f49566b2fff8646d53faa2`, `support/default_validator/default_validator.cc`, source SHA-256 `2901f589366382433562ec550b2f0c979ad94e3a3a4f737ef013bdd4fa334328`. The compiled checker digest and actual toolchain/image are qualification evidence, not fabricated manifest data.

Checker argv is service-generated: `default_validator <judge_input> <judge_answer> <empty_feedback_directory> [allowlisted_flags]`; contestant output is stdin. Those paths are allocated by the private adapter, never submitted by callers. Run checker separately after the user program: the user sees only executable/current input/work area and has no answer/checker/feedback access. Checker sees only its program, current input/answer/contestant-output and empty feedback area. Reference solutions never see answer files. No network, credentials, host paths or sibling process secrets are exposed.

The typed DEFAULT checker configuration contains pinned implementation identity, profile, caseSensitive and spaceChangeSensitive booleans, and explicitly nullable floatAbsoluteTolerance/floatRelativeTolerance decimal strings. Both null disables float comparison. Nonnull tolerances are exact finite nonnegative decimal lexemes with maximum64 characters and semantic range0..1; zero remains a valid enabled strict numeric tolerance. Normalization may add a leading zero to a source fractional lexeme while retaining the original lexeme in evidence. `float_tolerance x` maps to both effective valuesx; absolute-only/relative-only source flags map accordingly. Unknown/duplicate conflicting source flags or out-of-profile tolerances are unsupported, not ignored. Generate argv in deterministic order: case_sensitive iftrue, space_change_sensitive iftrue, float_absolute_tolerance/value ifnonnull, float_relative_tolerance/value ifnonnull. No free-form arguments are accepted.

Pinned behavior is whitespace-token comparison and case-insensitive text by default. The explicit flags enable case/whitespace sensitivity. Floating comparison is disabled unless configured; finite numeric tokens pass absolute OR relative tolerance, relative scaled by the absolute reference value. NaN/infinity are not accepted as numeric floats. Missing/extra output tokens are WA. Binary token behavior, including embedded NUL handling through the pinned C-string comparison/numeric parsing, is defined by the exact checker source and regression fixtures; do not claim byte-complete string equality or reinterpret its behavior. Preserve mature checker source; do not replace it with TrimSpace or a homegrown token/numeric approximation.

Exit42 is AC, exit43 is WA. Any other exit, signal, timeout, sandbox failure, invalid result, checker output/memory exhaustion or internal judge-error assertion is IE. Raw feedback can contain hidden answers and remains private; expose only bounded safe diagnostic codes. Contestant program output exhaustion is OLE before checker; checker failure cannot be mapped OLE/WA for the user.

An input validator receives exactly the current test's input on stdin, with no arbitrary caller arguments, no answer file and no reference/user program output. The controlled language profile generates its argv from the frozen source reference. Exit42 means valid input; any other exit, signal, timeout or resource/sandbox failure fails technical validation with private diagnostics. Source `input_validator_flags`, group-specific parameters or argument-dependent input validation are unsupported by this profile and retained as PACKAGE_UNSUPPORTED evidence, never silently omitted. Every listed validator must validate every applicable input. At least one real input validator is required by the current pinned technical validation flow.

## Technical validation results

Terminal validation run results have exactly five required object members: structure,statement,testData,validators,referenceSolutions. Each has required boolean passed and a nonempty evidence array. PENDING/RUNNING may retain the baseline empty results object while no final report exists; an empty in-progress object is never publication evidence. Evidence uses check,subjectSha256/null,logObjectKey/null,summary; raw logs stay private, summaries are bounded. There are no truthy strings, `status:"ok"` aliases, omitted checkpoints, or empty evidence accepted as terminal proof. A PASSED run requires all five passed=true, errors=[], finishedAt and actual pinned toolchain/image/config identity. A FAILED run retains at least one actual error and false failed checkpoint; skipped checkpoints have passed=false and explicit NOT_RUN/due-to-prior-failure evidence, never invented successful execution. Missing required validators or a bad accepted reference blocks validation/publication. Run all required checks through the mature pinned verifyproblem flow; format adaptation alone cannot suppress errors.

Package/runtime acceptance must run pinned checker24 upstream regression fixtures, case/whitespace/float/binary-output fixtures,42/43/other/crash/time-limit mapping, user answer-access denial, source/normalized archive golden bytes, per-case order and first-failure aggregation, semantic schema constraints, missing validators, reference failures and path/link/resource attacks. Schema/document publication does not claim these execution tests passed. Real untrusted execution requires the Linux qualification gate.
