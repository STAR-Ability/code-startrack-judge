# Upstream upgrade policy

An upgrade begins with an Issue containing the current and proposed immutable versions, reason, scope, consumers and rollback/recovery constraints. A newer version alone is not a reason. Security fixes may justify an expedited review, but do not remove compatibility, provenance or isolation requirements.

1. Review upstream release notes, commit diff and security advisories against the current lock. Identify generated protocol changes, runtime flags/defaults, package formats, compiler assumptions and all relevant changes in LICENSE/NOTICE or bundled content.
2. Review actual dependency resolutions and base-image packages, not only the top-level tag. Resolve commits and verify source/download checksums. Keep source, owned adapter changes and patch rebases distinguishable. Record any fork and its relationship to the original upstream.
3. Test on a temporary branch or isolated development environment. Update adapters deliberately, preserving the published contract. If the required behavior conflicts with a contract, open an explicit contract/ADR decision rather than silently changing it.
4. Run targeted unit/protocol/DTO and package regression tests. Include the old package fixtures, default checker token/floating-point/case semantics, rejected unsupported formats and negative reference solutions. Append validation runs for tool upgrades. Create new artifacts/versions when an independently versioned adapter changes normalized content or execution semantics; retain original artifacts, version references and validation evidence. Evidence-only re-review artifact identity needs the explicit resolution tracked in [contract question Q-005](../contracts/open-questions.md), rather than an invented adapter-version change.
5. For go-judge, go-sandbox, seccomp profiles, toolchains or worker/runtime image changes, verify on the intended Linux environment: startup must fail closed, cgroup/CPU/wall/memory/output limits, namespace/process/filesystem/network isolation, compiler/checker/validator confinement and task cleanup. Review security-sensitive changes independently. A green portable workflow cannot satisfy this step.
6. Resolve license and secret-handling gates, regenerate the actual distribution inventory/SBOM and attribution bundle, and record the real image digest and test evidence. Verify notices in the built image, not only in this repository.
7. Update the lock and [compatibility matrix](compatibility-matrix.md), documentation, changelog and relevant ADRs. Remove obsolete patches only after proving upstream contains the required fix. Land validated work on `dev`, then use the [release process](../releases/process.md) for promotion through a PR to `main`.

No runtime dependency may follow `latest`, upstream branch heads or an unbounded resolver in a release build. Toolchain security patch upgrades are explicit lock changes with verification. Never reinterpret an old JudgeTask's frozen runtime/config/image as the new runtime, or re-normalize an existing immutable artifact in place.

If an upgrade fails, keep the existing validated combination. If a shipped release requires rollback, evaluate database forward-migration compatibility, accepted tasks and retained image availability first. A Git revert does not undo a schema change or make a historical judgment reproducible. Reproduction uses the recorded artifact, adapter, language configuration, sandbox version, limits and image digest in an isolated environment; continued production support of every old executable is a separate security decision.
